# SPEC — backend internals

## Architecture (decisions + why)

- **JOOQ DB-first, no ORM**: the Liquibase SQL schema is the source of truth and codegen from a live DB guarantees code/schema lockstep at compile time. JPA was rejected — triggers, JSONB metadata, PG native enums and hand-tuned queries don't fit entity mapping.
- **Joda-Time in the domain** (`jackson-datatype-joda` registered): historical choice kept for consistency; `DateTimeHelper` is the single crossing point to `java.time` and uses the system zone — timestamp conversion is timezone-sensitive.
- **Firebase behind an optional Lambda proxy**: `firebase.lambda.name` set → token checks go through `lambda/firebase-proxy`; blank → in-process Admin SDK. Both paths must stay behaviorally identical. The reason is **network, not instance size**: App Runner runs with `EgressType: VPC`, so the container has no route to the internet and cannot reach Google — the alternative would be a NAT Gateway (~$32/mo). The Lambda uses **SnapStart on the `live` alias**, so `firebase.lambda.name` must stay **qualified** (`ipredencao-firebase-proxy:live`); `$LATEST` gets no snapshot. Consequences: deploy only via `lambda/firebase-proxy/deploy.sh`, the single entry point (SAM publishes a version and moves the alias; a bare `update-function-code` touches only `$LATEST`, leaving prod silently on the old code without a snapshot), and the invoke policy must cover the qualified ARN. The invoking client sets explicit timeouts (`clientExecutionTimeout` 12s) so a slow Firebase never outlives the frontend's 25s login budget.
- **LocalStack stands in for S3 only** (photo storage); empty `cloud.aws.s3.endpoint` means real AWS.
- **Session model**: app-issued HS256 JWT; refresh tokens stored SHA-256-hashed in `sessoes_usuario`. `JwtAuthenticationFilter` re-validates against the DB on every request (user still active, role claim still equals current profile) — deactivation/role changes bite immediately, at the cost of one query per request. The filter writes a single `AuthUser` (id, email, profile) as the `SecurityContext` principal plus the `ROLE_<perfil>` authority; `SecurityUtils` reads that context only (id from `AuthUser`, groups from the authority) and never reopens the JWT. Authorization is deliberately double-layered: `SecurityConfig` matchers AND `@PreAuthorize` on controllers.
- **Role groups live in `config.Roles`** and are derived from the domain `PerfilAcesso`, which mirrors the DB enum and is checked against the JOOQ-generated enum by `RolesTest`. Matchers consume `anyNames()` / `staffNames()` / `elderNames()` / `adminNames()`; `@PreAuthorize` delegates to the same groups through the `roles` bean (`@roles.staff(authentication)`, etc.). Programmatic checks use those names via `SecurityUtils.hasAnyRole(...)` — profile strings are not redeclared in authorization code. The authority is `ROLE_<perfil>`, granted by the JWT filter; nothing else confers permission. The matcher decides **before** the annotation, so a path-wide matcher silently overrides a more permissive `@PreAuthorize`: POST reads (`/pessoas/search`, `/serving-areas/search`, …) need their own method-scoped matcher or they fall into the write catch-all.
- **`MEMBER` and `MEMBERSHIP_CANDIDATE` are profiles without access.** They exist on `perfil_acesso` / `PerfilAcesso` so a `usuario` can be tied to a pessoa without entering any matcher or `@PreAuthorize` group. `Roles.anyNames()` is an explicit list (`BOLETIM`, `DIACONO`, `PRESBITERO`, `ADMIN`) and must not be rebuilt from `PerfilAcesso.values()`. Login still requires `usuario.active`; even if activated, these profiles cannot pass any current matcher.
- **User–person link** (V014): `usuario.person_id` is optional, `UNIQUE`, FK `pessoa(pessoa_id) ON DELETE SET NULL`. Wire field `personId` on `CreateUserRequest` / `UserSummaryResponse` (both records). PATCH `UpdateUserRequest` stays a class so it can tell omitted `personId` (keep) from `personId: null` (unlink). Missing pessoa → 400 `Pessoa não encontrada`; another user already linked → 409 `Esta pessoa já está vinculada a outro usuário`. `UsuarioRepository` has one `find(UsuarioQuery)` (plus `count`); email matches `lower(trim(...))`.
- **`processForm` user guarantee** is after the pessoa/form transaction commits. `UserService.ensureInactiveUserForPerson` runs for the principal when the aggregator is 2 or 3 (`MEMBER`) or 5 (`MEMBERSHIP_CANDIDATE`). Pastors, rol à parte and everyone else are skipped. Matching is `lower(trim(pessoa.email))` only. Existing Firebase/DB users are reused when the email is unambiguous; otherwise a disabled Firebase identity (no password) and `usuario` `active=false`, `provider=EMAIL` are created. Failure does not roll back the pessoa: HTTP 200, `ProcessarFormularioResponse.mensagem` becomes `A pessoa foi processada, mas não foi possível criar o usuário.` Success leaves `mensagem` null. A Firebase uid created in that attempt is compensated if the DB insert fails; identities that already existed are never deleted. Password remains the existing “Reenviar convite” flow — processForm never sends mail.
- **A module with any endpoint that `MEMBER`/`MEMBERSHIP_CANDIDATE` must reach** (they're in no `Roles` group — see above) gets an **explicit `.authenticated()` matcher** in `SecurityConfig` for its base path, not `hasAnyRole(...)`: the matcher decides before the annotation (see Role groups), so `hasAnyRole(...)` would 403 before `@PreAuthorize` ever runs. `.authenticated()` is behaviorally identical to riding the final `anyRequest().authenticated()` catch-all, but written out so the route reads as decided-on, not forgotten. Every real distinction (`STAFF` vs. any authenticated, or a bean resolving something row-specific) lives in `@PreAuthorize` per method — the one place that can see a specific path variable and pick the right check for it. Precedent: `/api/ebd/**` (`EbdController`). A bean resolving something row-specific (e.g. `EbdAccess.currentPersonId`, from `AuthUser` → `UserService.getUser(id).personId()`) can back such a check when the permission depends on a row, not a `perfil_acesso` — EBD had one for "is this person the teacher of this class" (`EbdAccess.isTeacherOf`) until the team simplified that permission back to plain `STAFF` in review; the pattern remains available for a future case that needs it.

## Data-model invariants

- History is trigger-written, never by application code: `pessoa` → `pessoa_history` (AFTER INSERT/UPDATE), `person_note` → `person_note_history` (BEFORE UPDATE). Changing `pessoa` columns requires recreating `insert_pessoa_history()` in the same migration (precedent: V005).
- `updated_at` is set by a trigger — don't set it in code.
- Hard deletes only; there is no soft-delete. Delete history rows before the parent row (FK), as in `PessoaRepository.deletePregnancy`.
- `updated_by → usuario` is `ON DELETE RESTRICT` (V008): a user who authored any record cannot be deleted.
- Bilingual schema is intentional: legacy PT tables (`pessoa`, PK `pessoa_id`) coexist with EN tables (V006+), and EN tables FK into PT ones (`official_act.person_id → pessoa(pessoa_id)`). Do not "fix" the inconsistency.
- `CategoriaEnum` / `OfficialActFormEnum` / `OfficialActTypeEnum` hardcode DB seed ids — any seed change is a paired enum change. They serialize as objects and deserialize from a bare id (`@JsonFormat(OBJECT)` + delegating `fromId`).
- Name search is accent-insensitive (`unaccent` extension + `QueryConditions.addUnaccentedLike`).

## Domain invariants

- **Official acts**: `metadata` is JSONB validated in `OfficialActService` against the per-form schema encoded in `OfficialActFormEnum` (required fields; PERSON_REF shape). Creating an act applies side effects to the person — categoria, and possibly baptism/profession-of-faith/death dates — unless the form sets `skipEffects`. Create/update find-or-create a `minute` row (`official_act.minute_number` is an FK); body `minuteDate` is a hint (create or fill-if-empty) and never overwrites a date already stored — correction is `PUT /api/official-acts/minutes/{n}`. Deleting an act reverts **categoria only** (to the value held immediately before the act); dates stay. Baptism certificates and transfer letters are not API resources — the SPA composes them from existing official-act, pessoa and serving-area reads and renders PDF or DOCX. After an incoming transfer-letter request is generated, the SPA calls `PATCH /api/pessoas/{id}/categoria` with legacy wire field `categoriaId` to move categoria 15 → 14. That endpoint is `DIACONO`+, preserves every other `pessoa` column and updates only `categoria_id`/`updated_by` (the trigger maintains `updated_at` and history).
- **Admission order numbers** come from the global sequence `official_act_admission_order_seq`; an MNC→MC promotion (Art. 24,d) reuses the person's latest existing number instead of drawing a new one. Suppressible per form.
- **Pregnancy**: a `pessoa` in categoria 29 (30 = temporary secrecy). Create copies the mother's campus and family-head address and creates MAE/PAI relationships; guards: father ≠ mother, due date not in the past. Registering a birth moves the baby to categoria 16 (aguardando batismo infantil) by default. `close` refuses while official acts reference the person, then hard-deletes (history first).
- **`pessoa.categoria_id` is `NOT NULL`** (V011). The filter below leans on it: `categoria_id <> 30` is SQL three-valued, so a single null row would silently vanish for every non-elder. `PessoaService.create` rejects a null categoria with 400 so the constraint is never the thing the user hears from; `update` leaves categoria untouched when it comes in null, so only create can violate it.
- **Secrecy is row-level security, and categoria 30 is its only handle.** `PessoaRepository.buildConditions` adds `categoria_id <> 30` whenever the caller is below `PRESBITERO` (`SecurityUtils.hasAnyRole(Roles.elderNames())`, read from the `SecurityContextHolder` authority — not by reopening the JWT). Because every read goes through `find`/`count`, that one condition closes find-by-id (which becomes a 404, not a 403 — a 403 would confirm the row exists), paginated search, the arbitrary-query report and the summary's per-category count. The rule itself lives in `ConfidentialRows` (the category id, the "can this caller see it" test, and the JOOQ condition), because `find`/`count` are not the only queries that touch `pessoa` — anything that selects the table on its own has to apply it, and four such queries do:
  - `loadRelationshipsForPeople` filters **both** ends of each relationship (the leak is the mother's card, since the link is written baby → mother), and `mapRelationship` filters the related person's name lookup.
  - `EnderecoRepository.getPersonIdsFromAddresses` filters the residents of an address: a pregnancy inherits the family head's `endereco_id`, so an unfiltered `pessoaIds` would announce the row's existence on the mother's own card.
  - `ServingAreaMemberRepository.findReportPeople` filters the participation report, whose categories come **from the request body** — without it, asking for categoria 30 lists every secret pregnancy by name to any role.
  - `/pessoas/{id}/history` and `GET /pessoas/{id}/notes` are `DIACONO`+; `POST /pessoas/{id}/relacionamento` likewise. They reach person-owned data by id, so GET history/notes and the relationship endpoint re-check visibility first (the relationship endpoint checks **both** ends, since its idempotent response carries the other person's name). The GET matchers for history and notes sit above the GET catch-all of `/pessoas/**`, or `BOLETIM` would pass the matcher and only fail at `@PreAuthorize`.
  - **The escape hatch is an argument**: `find`/`count` take a `ConfidentialAccess`, defaulting to `CALLER`. `INTERNAL` has two callers: `PregnancyService.reloadWithRelationships` (must see the row it just wrote) and `EnderecoService.delete` (integrity count that must not depend on who is asking). Because internal reads are explicit, `SecurityUtils.hasAnyRole(...)` fails **closed** when there is no `Authentication`.
  - **Writing secrecy is `PRESBITERO`+**, enforced in `PregnancyService`, not by a matcher, because it depends on the payload and current state: `create` with `confidential: true` and `update` that turns secrecy on raise `AccessDeniedException` (403); editing, registering birth for, or closing a row already in categoria 30 is simply a 404, since the filtered read can't find it. A `DIACONO` keeps the full categoria-29 cycle.
- **Pendência (`bookmark`) is a query filter, not a hidden field.** The value travels on every `Pessoa` payload. `SecurityUtils.hasAnyRole(Roles.staffNames())` only decides whether `PessoaRepository` applies the query's `bookmark` clause: asking for `bookmark: true` in search or `generate-report` as `BOLETIM` is ignored — it does not 400, and it does not shrink the result.

- **Serving areas** (V009, `serving_area` + `_position` / `_team` / `_member`): ministries/societies/governing bodies. Named `serving_area` (not `church_service`) to avoid colliding with the service layer; UI says "Serviço".
  - **Soft-delete exception (só o serviço)**: a área (`serving_area`) tem `active` — desativar oculta da listagem padrão; cargos e equipes não têm flag de ativo (exclusão só quando nada referencia). Membership history lives in `serving_area_member_history` (DB triggers on INSERT/UPDATE/DELETE; `deleted_at` set on removal).
  - **Vínculo atual** = row present in `serving_area_member` (ending a mandate = DELETE; history preserved). Drives supervisor uniqueness, listagem derivada (`teamCount`, `memberCount`, `coordinatorCount`), detail sections, the person card, and reports.
  - **Membresia com equipes**: quando o serviço tem ao menos uma equipe, vínculo `MEMBERSHIP` exige `teamId` (validado no service); coordenação pode ficar no escopo geral (`team_id` nulo) ou de equipe. **Supervisão é sempre do serviço inteiro**: um vínculo `SUPERVISION` com `teamId` é rejeitado.
  - **One supervisor per area** (a `SUPERVISION`-kind vínculo). Not auto-closed on change: the service rejects a second supervisor (409) — remove the current one first. The supervisor is conventionally a presbítero but this is **not** validated (no stable handle to "Conselho"; `system_key` was deliberately dropped).
  - **`position_id`/`team_id` FKs are `NO ACTION`** (not RESTRICT/SET NULL) so the area's `ON DELETE CASCADE` can drop members+cargos+equipes in one statement; "in use" protection lives in the service layer. `person_id → pessoa(pessoa_id) ON DELETE CASCADE` (person delete removes their vínculos).
  - **Cargo `kind` is immutable once the cargo has any vínculo** — else a MEMBERSHIP→SUPERVISION flip would retroactively promote everyone and bypass the supervisor rule. O nome do cargo segue editável. Listagem ordena por `kind` (SUPERVISION → COORDINATION → MEMBERSHIP), depois nome.
  - **Duplicate guard**: identical vínculos (same area+person+cargo+team) can't coexist (service-layer check; unique index `uq_serving_area_member` is the backstop).
  - **Seeds**: four fixed areas (Conselho, Junta Diaconal, Presbítero/Diácono em disponibilidade) created as ordinary areas, each with one MEMBERSHIP cargo. No special protection; operational rule is not to rename them.
  - **PG-native enum** `serving_area_position_kind` → plain string on the wire (`.name()` at the JOOQ boundary), not a seed-table enum.
  - **Report/member queries are generic filters** — `ParticipationReportQuery` and `ServingAreaMemberQuery` accept optional `categoryIds` + `campus` (equality) and the service passes them through as-is; the caller (FE) decides eligibility (serviços usam categorias 1-8 + campus SEDE). Não há regra de elegibilidade hardcoded no backend.
  - **Repositories** follow the `PessoaRepository.find(query)` shape: one generic `find(<Query>)` per repo (id is just a filter); writes return via `RETURNING` where there are no derived JOIN fields, otherwise the service re-fetches through `find`. Wire query objects are records (member query has a builder to avoid positional null-soup).

- **EBD** (`V015__ebd.sql`: `ebd_cycle` / `ebd_class` / `ebd_enrollment(+history)` / `ebd_lesson` / `ebd_material` / `ebd_attendance`, uma única migration). Plano completo em `docs/EBD_ANALISE_E_PLANO.md` (raiz do monorepo). Tables named `ebd_*` (not `sunday_school_*`, the doc's original suggestion) per explicit user decision. Passou por uma segunda rodada de simplificação em revisão do PR (removeu a distinção "turma fixa", colapsou matrícula/presença em endpoints únicos) — ver pontos abaixo.
  - **Toda turma pertence a um ciclo** (`cycle_id` `NOT NULL`) e funciona da mesma forma — não existe mais "turma fixa" (matrícula só por STAFF) vs. "não-fixa" (automatrícula); ambas as vias (automatrícula e inclusão administrativa) valem pra qualquer turma agora. `EbdClassForm.cycleId` é obrigatório na criação; na edição, omitido mantém o valor existente (mesmo padrão de `name`/`description`).
  - **`TEACHER` não é um `perfil_acesso`** — é só `ebd_enrollment.role`, a mesma tabela/coluna que carrega `STUDENT`, e hoje é **puramente informativo**: não concede permissão (ver abaixo) nem condiciona a ativação da turma (a exigência de professor vinculado pra ativar existia só pra turma fixa e foi removida junto com o conceito).
  - **Gerenciar uma turma é STAFF, ponto** — sem a granularidade "ou o professor da própria turma" que existiu numa versão anterior (`EbdAccess.isTeacherOf`, removida a pedido do time em revisão do PR: de início, diácono/presbítero/admin bastam). `updateClass`, `listEnrollments`, `createLesson`, `addClassMaterial` são `@PreAuthorize(STAFF)` direto no controller; `updateLesson`/`deleteLesson`/`addLessonMaterial`/`deleteMaterial`/`listAttendance` recebem o id da aula/presença/material no path, não o da turma, então a mesma checagem (`EbdService.requireStaff`) fica no service em vez da anotação.
  - **Matrícula: um único par de endpoints** (`POST`/`DELETE /api/ebd/classes/{id}/enrollments[/{enrollmentId}]`) serve automatrícula e matrícula administrativa — `personId` no body presente = STAFF agindo em nome de alguém (qualquer role); ausente = o próprio chamador (sempre `STUDENT`), decidido em `EbdService.addEnrollment`/`removeEnrollment` porque `@PreAuthorize` não enxerga o body. No `DELETE`, um não-STAFF só remove a própria matrícula `STUDENT`. `DELETE .../enrollments/me` continua existindo como atalho pra quem não sabe o próprio `enrollmentId` — resolve e delega pro mesmo `removeEnrollment`; não há `POST .../enrollments/me` mais (o `POST` colapsado já cobre self-service com body vazio).
  - **`ebd_cycle.active`**: só 1 por vez, índice único parcial (`uq_ebd_cycle_single_active`); `assertSingleActiveCycle`/`assertUniqueCycleName` checam via `find(...).isEmpty()` (não há `existsByName`/`existsOtherActive` dedicados no repositório — dobrados no `find` a pedido do time em revisão).
  - **Visibilidade**: STAFF vê qualquer status de turma; qualquer outro autenticado só vê turmas `ACTIVE` — pedir o detalhe de uma turma `DRAFT`/`CLOSED` sem essa visibilidade é 404, não 403 (mesmo padrão da categoria 30: não confirma a existência da turma alheia). Mesma régua pra aula/material, mas em 403 em vez de 404 (a turma já é conhecida/visível nesse ponto — só falta permissão): STAFF vê tudo; aluno matriculado só vê aulas `PUBLISHED` e materiais de aulas `PUBLISHED` (materiais gerais da turma não têm esse filtro).
  - **Automatrícula/presença exigem `usuario.person_id` resolvido** (V014, não alterado pela EBD — decisão explícita do usuário de não mexer nesse vínculo). Sem ele, essas ações devolvem 409 orientando a pedir a um admin para vincular o usuário; não existe fluxo de autovínculo.
  - **`/api/ebd/**` tem um matcher explícito `.authenticated()` em `SecurityConfig`** (não `hasAnyRole(...)`) — ver a entrada sobre módulos que `MEMBER`/`MEMBERSHIP_CANDIDATE` precisam alcançar, acima.
  - **Aula**: sem `content` nem `displayOrder` — descrição + material bastam, e a ordem de exibição é sempre por `lessonDate` (por isso ela é `NOT NULL`, validada em `EbdService.validateLessonForm`).
  - **Materiais**: `ebd_material` (`lesson_id` nulo = geral da turma, preenchido = de uma aula) é guardado como `BYTEA` (`file_data`) na própria linha — **decisão explícita do usuário de não usar S3** para isto (reafirmada em revisão do PR), diferente do padrão de foto de pessoa (`S3Service`), que continua intocado. Um único modelo `EbdMaterial` cobre listagem e download (campo `data` fica `null` na listagem — `EbdMaterialRepository.find` nunca seleciona `file_data`; só `findWithData`, usado exclusivamente pelo download, carrega o BYTEA). `spring.servlet.multipart.max-file-size=10MB` já cobria o caso, sem precisar de ajuste.
  - **Ementa é um arquivo, não texto** (decisão do usuário, pós-review): no máximo um por turma, guardado direto em `ebd_class` (`syllabus_file_name`/`syllabus_content_type`/`syllabus_file_size_bytes`/`syllabus_file_data`, mesmo padrão BYTEA de material) em vez de uma linha em `ebd_material` — é propriedade da turma em si, não um "material geral" entre outros. `EbdClass` só carrega o metadado (`EbdClassRepository.find` nunca seleciona `syllabus_file_data`); `POST/DELETE /api/ebd/classes/{id}/syllabus` (STAFF) substitui/remove o arquivo inteiro (nunca parcial), `GET .../syllabus/download` (mesma visibilidade de material geral: STAFF sempre, aluno matriculado também) carrega o BYTEA via `EbdClassRepository.findSyllabusContent`.
  - **Presença: um único trio de endpoints** (`POST /api/ebd/lessons/{id}/attendance` cria, `PATCH`/`DELETE /api/ebd/attendance/{id}` atualiza/remove) serve professor e aluno — mesmo princípio de `personId` no body da matrícula: presente = STAFF marcando/alterando/removendo em nome de alguém; ausente = o próprio chamador. Um não-STAFF só altera/remove a própria presença (`EbdService.requireOwnAttendanceOrStaff`). O aluno pode desfazer a própria marcação a qualquer momento (`DELETE`) — antes só existia marcar, nunca desmarcar. `ebd_attendance` referencia `ebd_enrollment`, não `pessoa`/`ebd_class` direto — só quem tem matrícula pode ter presença, turma+pessoa vêm por transitividade. `markAttendance` exige aula `PUBLISHED` (403 senão) e matrícula `STUDENT` ativa na turma da aula (409 "não matriculado" — mesmo tratamento de estado que "sem pessoa vinculada"); presença duplicada é 400 (índice único `uq_ebd_attendance` como backstop). Sem `self_reported`: quem marcou/alterou por último já dá pra saber por `updated_by` — nem tabela de histórico própria (diferente de `ebd_enrollment_history`), `updated_by`/`updated_at` bastam. `GET /api/ebd/lessons/{id}/attendance/me` (`EbdService.getSelfAttendance`) resolve um gap descoberto testando o frontend: sem isto o aluno não tinha como saber, ao abrir a lista de aulas, se já tinha marcado presença numa sessão anterior. 404 cobre "nunca marcou", "não está matriculado" e "sem `usuario.person_id` resolvido" da mesma forma — o chamador só precisa saber se existe ou não, não o motivo.

## Transactions / concurrency

- `@Transactional` per service write method (`readOnly = true` for reads); JOOQ rides the Spring-managed transaction. No optimistic locking — last write wins; low write contention is assumed (single congregation).
- Admission numbering relies on the PG sequence for concurrency safety.

## Out of scope / deprecated

- `informacoes_adicionais` was dropped in V005 (data migrated to `person_note`) — never reference it.
- Facebook login is a deliberate `UnsupportedOperationException` (501) stub.
- `scripts/backfill/` is a completed one-shot migration — don't rerun it.
- `scripts/user-backfill/` is the operational user↔person backfill (dry-run default, `--apply` explicit). Do not send mass invites; password is the existing “Reenviar convite” flow.
- No multi-tenancy: single church by design.
